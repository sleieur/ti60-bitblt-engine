# bbShow —— 2D 图形渲染加速引擎完整演示程序

一块板子、一个程序、9 个场景，把赛题二（基于 RISC-V 与 FPGA 异构架构的 2D 图形渲染加速引擎）的
基础要求和三条高阶挑战全部覆盖。上电后用串口（115200 8N1）按键切换，或让它自动轮播直接录视频。

## 2. 编译与运行

### 2.1 编译（两种方式，结果一致）

**A. IDE 里编译（推荐）**
Efinity RISC-V IDE → 打开 `par/ddr_demo_ti60/embedded_sw/soc` 下的工作区 → 选中 `bbShow` 工程 → Build。
产物：`bbShow/build/bbShow.elf` / `.bin` / `.hex`。

**B. 命令行编译**
```powershell
# 在 bbShow 目录下执行
.\build.ps1
```
脚本会自动寻找 IDE 自带的 `make.exe` 与 `riscv-none-elf-gcc`，不依赖中文路径。

### 2.2 上板

1. **先烧逻辑**：Efinity Programmer → JTAG → `par/ddr_demo_ti60/outflow/ddr_demo_ti60.bit` → Start。
2. **再下软件**：IDE 里选中 `bbShow` → 用 `bbShow_ti.launch` 下载运行（OpenOCD + GDB，流程与 bbFill 相同）。
3. 串口打开（115200 8N1），能看到启动日志和每秒一行的统计。

> **重要**：`RENDER_MODE` 只能在显示启动之前写。所以**每次重新运行程序前都要重新加载一次 `.bit`**
> （或重新上电）。不重载的话串口会打印
> `!!! cannot enter BitBlt mode !!!` —— 这是 FPGA 侧显示逻辑还在跑导致的，不是软件问题。

### 2.3 串口按键

| 键 | 作用 |
|---|---|
| `1` … `9` | 直接跳到第 N 个场景（并关闭自动轮播） |

| **空格 / 回车** | **下一个场景**（录视频就按这个，不用记编号） |
| `a` | 开/关自动轮播（默认开，每张卡 7 s；极限测试 10 s。游戏不看计时，Boss 被打掉就切，50 s 只是兜底） |
| `+` / `-` | 当前场景的对象/精灵数 ±100（场景 2、4 有效），现场演示"再多一点 CPU 就扛不住了" |
| `r` | 重置帧率统计 |
| 在 SPRITE LIMIT（场景 6）里：等它自己收敛即可，不用操作 | |
| 在 STARFALL（场景 7）里：`p` 自动/手动驾驶，`j` `l` `i` `k` 移动，`r` 重开 | |
| 在 IMAGES（场景 8）里：**空格** 暂停/继续，**`+` / `-`** 调播放速度（1~60 fps） | |

## 3. 九个场景

> 下面每个小标题的编号 = 串口按键号，和屏幕上显示的编号一致。

### 场景 1 —— INTRO
上电首页，列出全部场景与操作提示。适合作为视频开头。

### 场景 2 —— SPLIT FILL：300 个方块，CPU vs 硬件
* 屏幕左半边 `SOFTWARE CPU`：普通 C 代码逐像素写 DDR，**没有 DMA、没有引擎**。
* 屏幕右半边 `HARDWARE BITBLT`：300 条 FILL 指令由引擎执行。
* 两边是**同一组方块**（同一种子生成的坐标/颜色/速度），所以能一眼看出谁跟得上。

屏上读数：
```
SOFTWARE CPU      44 MS/FRAME          ← CPU 画完一整幅 640x720 所需的纯计算时间
                  22 FPS EQUIV         ← 1000 / 44
HARDWARE BITBLT   60 FPS               ← 引擎每秒换页次数（硬件上限）
SQUARES 300
```
左上角白底黑字的 `FPS: NN` 是显示通路里的硬件计数器（每秒换页数）。

**看点**：右边 60 Hz 连续运动；左边每隔几帧才跳一下（CPU 单帧要几十毫秒）。
按 `+` 加到 800、1000，左边越来越卡，右边仍然是 60。

### 场景 3 —— SPLIT COPY：整屏大图快速切换
左半边 CPU 用 `for` 循环把 1280×720 图的左半幅拷进缓冲区；右半边一条 COPY 指令。
四张图每帧轮换，右边平滑切换，左边跳帧。读数含义同场景 1。

### 场景 4 —— COLOUR KEY：颜色键控去背
300 个 48×48 精灵（品红背景，圆形/菱形/方形）在渐变棋盘背景上移动；
屏幕底部一排 20 个精灵放在奇数 x 位置，**首尾两个各有一半在屏幕外**，用来验证裁剪。

屏上读数：`KEY SPRITES 300  /  NO MAGENTA LEAK  /  EDGE CLIPPING OK`

**验收**：屏幕上**一个品红色像素都不应该有**（已用 PC 预览程序逐像素验证：0 个）。
看底部那排——第一个和最后一个是被"切"掉的半个圆。

### 场景 5 —— ALPHA BLEND：硬件透明度混合
彩条背景上 5 个固定方块，alpha = 0 / 64 / 128 / 192 / 255，上方用硬件字体标出数值；
下面 8 个移动方块的 alpha 在 0→255→0 之间来回扫。
底部写明了混合公式 `OUT = SRC X ALPHA + DST X 1-ALPHA`。

**验收**：0 完全看不见、255 完全不透明、中间三块逐级变淡，透过方块能看到背后的彩条。

> 说明：本引擎的 alpha 是**整块统一透明度**（不是逐像素 alpha 贴图），
> 所以方块四边都能看到——这正是"图层整体透明度"的正确表现。

### 场景 6 —— SPRITE LIMIT：Alpha + Color Keying 同时开启时的精灵数极限

赛题高阶挑战③的原文是"**在开启硬件加速（Alpha 混合 + Color Keying）的情况下，挑战保持 60 FPS
稳定运行时的同屏活动元素（Sprite）数量极限**"。这个场景就是为它量身做的纯压力测试，不做别的事：

* 背景只用**一条** FILL 指令铺满（不给引擎任何额外负担）
* 屏幕上每 4 个元素里有 3 个是**颜色键控精灵**（24×24，品红底），1 个是**半透明方块**
  （ALPHA，110/255）——两种加速运算在同一帧内同时工作
* 精灵数由 **AIMD 探针**自动控制：帧率 ≥59 就按步长上调（步长逐次翻倍，快速逼近），
  一旦掉帧就减半步长回退。屏上 `STEP` 就是这个步长
* **上限 2048**，远超引擎能力（一帧约 4000 个描述符，而一个 24x24 精灵就要 24 个），
  所以一定会压到掉帧——左上角 `FPS` 行变红显示 `BELOW TARGET` 就是那一刻
* 掉帧后探针回退，`SPRITES AT 60 FPS` 保持历史最高值
* 屏上大字是 `SPRITES AT 60 FPS`——**实测值，不是写死的**

左上角面板实时显示 `SPRITES / KEY / ALPHA / TASKS / STEP`，可以直接看出每帧向引擎提交了多少条指令。
这个数字也出现在场景 9 SUMMARY 页里。

> 为什么不用游戏场景来报这个数？游戏的每帧负载是波动的（Boss 出场时弹幕最密，平时很稀），
> 报不出一个稳定的极限值。压力测试场景负载恒定，才能给出可复现的数字。

### 场景 7 —— STARFALL：完整弹幕射击游戏
这是作品的"作品性"展示：一个能真的玩下去的纵向弹幕射击游戏，画面里**每一个像素都由引擎绘制**。

* 滚动星空：24 段竖向渐变做底，4 档速度的星点做视差，两团星云缓慢下落；
* 玩家机体 64×64（带引擎尾焰三帧动画、受击白色闪烁、无敌帧闪烁）；
* 三类敌机：拦截机（自机狙三连/五连）、重型机（16 发环形弹幕）、自杀机（蛇形追击）；
* 三阶段 Boss：环形爆发+自机狙 → 双旋臂螺旋+全屏环 → 三臂螺旋+大玉散射；
* 六种弹型（红玉/蓝玉/青玉/紫玉/米弹/大玉）由颜色键控绘制；
* HUD：血条（含分段刻度与受击红边泛光）、残机、擦弹数、精灵数、FPS、大字分数与最高分、
  Boss 血条+阶段指示，全部是 **硬件 ALPHA 半透明面板**（玻璃拟态）叠在游戏画面上；
* 自动避弹 AI：每帧为玩家脚下 9 个候选位置计算"弹幕到达危险度"（按子弹速度和到达时间加权），
  选最安全的一侧平移，因此可以不碰键盘录完整视频。

**看点**：同屏 300+ 精灵、每帧约 350 条指令、稳定 60 FPS；Boss 换阶段时有全屏冲击波与屏幕震动。

### 场景 8 —— IMAGES：多张大图快速切换（CPU vs 引擎同屏对比）

赛题要求"支持多张大图的快速切换"。这里做成**左右分屏、同一段画面**：

```
+-------------------------+-------------------------+
|   左半 640x720          |   右半 640x720          |
|   普通 C 代码 memcpy    |   一条 COPY 指令        |
|   约 38 ms/帧 -> 20fps  |   1.49 ms/帧 -> 60 fps  |
+-------------------------+-------------------------+
```

两边读的是**同一份 DDR 里的帧数据**（`0x06000000`），画面完全一致，唯一差别是"谁来把
像素搬到屏幕上"。进场景立即自动播放，左半明显卡顿，右半 60 fps 顺滑。

* 帧数据存成 **640x720**（半屏），每帧 900 KiB，步进 `0xE1000`，紧密排列
* 最多 **168 帧**（`IMG_MAX_PICS`），占 148 MiB
* **空格** 暂停/继续，**`+` / `-`** 调速度（1~60 fps，默认 60）
* 播放锁在 60 Hz 显示时钟上，帧率精确、与 CPU 忙闲无关
* 左侧面板实时显示 CPU 的 `MS/FRAME` 与 `HZ UPDATE`，右侧显示引擎的 `COPY 1.49 MS`

#### 为什么引擎这边毫不费力

引擎整屏 COPY 1280×720 是 2.98 ms，**半屏只要 1.49 ms**。60 Hz 每帧 16.7 ms，
所以哪怕 60 fps 换 60 张图，引擎也只占用 **9%** 的时间预算。CPU 那边同样 900 KiB
的拷贝要 38 ms（含 DDR 读写），**最多 26 fps**，而且一帧要占用 CPU 三个时间片。

#### 做成一段短片

```powershell
cd tools

# 视频截 3 秒
python vid2frames.py "D:\FPGA\clip.mp4" --start 5 --duration 3 --fps 60 --repeat 4

# GIF（14 帧 -> 每帧重复 12 次 -> 168 帧）
python vid2frames.py "D:\FPGA\gif\xxx.gif" --fps 60 --repeat 12

python img2assets.py
.\load_assets.ps1 -SkipRebuild
```

`--repeat N` 把每个源帧重复 N 次：播放时长不变，但用的是 N 倍数量的"大图"，
这样 60 fps 播放时既能看出连续动作，又满足"多张大图快速切换"的字面要求。

帧数与时长（168 帧上限）：

| fps | 可播放 | 说明 |
|---|---|---|
| **60** | **2.8 秒** | 满速，最直观 |
| 30 | 5.6 秒 | 顺 |
| 12 | 14 秒 | 像翻页 |

## 4. CPU vs 硬件"同屏实时对比"是怎么做的（可以拿去答辩）

**硬件侧**：引擎独占双缓冲，每帧结束时提交一条 frame-last 指令，引擎把后台页提交上屏、
自己领取下一个后台页，稳定 60 Hz。CPU 只发指令，不碰显存。

**软件侧**：同样的内容由 CPU 用普通 load/store 画进一块 DDR 缓冲区（`0x04000000`，640×720），
画完之后用**一条 COPY 指令**把它贴到屏幕左半边。

**为什么左边的刷新率不等于 "1000 / MS"？**
CPU 画一整幅要几十毫秒，如果让它一口气画完，整个提交流程就会卡住、右半边也跟着掉帧。
所以程序把 CPU 的绘制切成 20 条 36 行的横带，每帧只给它约 9 ms 的时间片，剩下的时间用来
维持 60 Hz 的提交节奏——**这是真实游戏里"按帧预算分配 CPU 时间"的标准做法**。
左边的刷新率因此是"每 9 ms 一片"，而屏上写的 `xx MS/FRAME` 是**实测的纯计算时间**
（逐条带累加计时，不含被切走的时间），它才是可以和引擎直接比较的数字：

| | 一幅 640×720 的纯渲染耗时 |
|---|---|
| RISC-V 软核（100 MHz，无 FPU，4 KB D-Cache，写透） | 约 30–50 ms |
| BitBlt 引擎（同样 640×720 的 FILL） | 约 0.8 ms（整屏 1280×720 也只要 1.6 ms） |

数量级相差 40 倍以上，这就是"把像素搬运从 CPU 手上拿走"的意义。

## 5. DDR 内存布局（`src/bbshow.h`）

| 地址 | 内容 | 大小 |
|---|---|---|
| `0x0100_0000` | FB0 显存页 0，1280×720 RGB565 | 0x1C2000 |
| `0x0180_0000` | FB1 显存页 1 | 0x1C2000 |
| `0x0300_0000` | IMG0 彩条 / IMG1 棋盘渐变 / IMG2 彩虹斜纹 / IMG3 同心圆 | 每张 2 MiB 间隔 |
| `0x0380_0000` | SHEET48：8 个 48×48 精灵（含玩家飞船） | 36 KB |
| `0x0382_0000` | SHEET32：8 个 32×32 精灵（敌人/子弹） | 8 KB |
| `0x0384_0000` | ALPHA96：96×96 透明度贴图 | 18 KB |
| `0x03A0_0000` | GLYPH：6 套调色板的 24×32 字形图集 | 每套 128 KB |
| `0x0400_0000` | CPUBUF：CPU 软件渲染缓冲区（左半屏），3 块轮转，stride 1280 | 每块 0xE1000 |
| `0x0600_0000` | 图片/短片帧数据包（由 `load_assets.ps1` 写入） | 最多 88 × 0x1C2000 = 155 MiB |

所有地址都在 `0x0100_0000 – 0x1000_0000`（引擎 SUBMIT 允许的 256 MB 窗口）之内，
且源区不与显存重叠（引擎要求如此）。

## 7. 串口日志样例

```
*** TI60 BitBlt engine demo: HDMI 1280x720p60 RGB565 ***
keys: 1-7 scene, a auto, +/- objects, r reset
building DDR content ...
  images, sprites and glyphs done (430 ms)
frame size 1c2000  stride 2560

[scene 0] INTRO : overview
[INTRO] hw 60 fps  cpu 0 ms  sprites 0  frames 60  err 0  uf 0

[scene 1] SPLIT FILL : left half rendered by C, right half by FILL tasks
[SPLIT FILL] hw 60 fps  cpu 38 ms  sprites 301  frames 120  err 0  uf 0
```

* `hw` = 引擎每秒换页次数，正常运行应稳定在 60；
* `cpu` = 上一次 CPU 整幅渲染的实测耗时；
* `err` 应恒为 `0`（非 0 表示 DMA 执行错误，`ERROR_CODE[11:8]`）；
* `uf` 应恒为 `0`（`1` 表示 HDMI 读 FIFO 下溢，即 DDR 带宽被打爆）。

## 8. 排错

| 现象 | 原因 / 处理 |
|---|---|
| 串口打印 `cannot enter BitBlt mode` | FPGA 逻辑没复位，重新加载 `.bit` 再运行 |
| 黑屏、`FPS: 00` | 用的是 `Mode: passive` 的 `.bit` 但没下程序；或程序没跑起来 |
| 画面有、但每次运行都要重烧 bit | 正常：`RENDER_MODE` 只能在显示启动前写 |
| 某个场景 `hw` 掉到 50 左右 | 该场景负载超过了 16.7 ms，按 `-` 减少数量，或属正常（游戏场景会自动让路） |
| `uf 1` | HDMI 读被挤爆，说明有场景把 DDR 带宽吃满了，记下是哪个场景 |
| OpenOCD `no device found` | `ftdi_ti.cfg` 里的 `device_desc` 已注释掉（只按 vid/pid 匹配），这是本机验证过的配置 |

## 9. 录视频建议脚本（约 3 分钟）

1. **0:00** 上电首页（场景 0）：念一遍这 7 个场景分别验证什么。
2. **0:20** 按 `1` → SPLIT FILL：指左右两半"同样的方块"，说"左边是 CPU 一条条写的，
   右边是引擎。左上角 FPS 60，左边写着 38 ms/帧"。按 `+` 两次加到 500 个，让观众看左边更卡。
3. **0:50** 按 `2` → SPLIT COPY：整屏大图切换，右边平滑、左边跳。
4. **1:10** 按 `3` → COLOUR KEY：强调"屏幕上没有一个品红色"，再指底部被切成半圆的精灵。
5. **1:30** 按 `4` → ALPHA BLEND：从 0 到 255 逐个指，说"透过 64 那块能看到背后的彩条"。
6. **1:50** 按 `5` → GAME：等 15 秒，让精灵数自己爬上去，念 `SPRITES` 和 `MAX SPRITES AT 60 FPS`。
7. **2:30** 按 `6` → SUMMARY：把引擎能力寄存器、CPU 38 ms、硬件 60 FPS 一屏念完。
8. 最后切回场景 1，按住 `+` 到 1000，停在左边的卡顿上收尾。

> 自动轮播：除极限测试（10 s）外每张卡 7 s；游戏场景不看计时，Boss 被打掉 → STAGE CLEAR → 自动进下一场。
> 整轮最坏 116 s（7×8 + 50 + 10），保底压在两分钟内；实际打赢约 90 s。
> 录制时每段前面接一张剪辑里加的介绍页，所以现场停留时间只需要够拍一条干净的效果。
